# FHSS + TDD 硬件时间戳同步引擎说明

本项目实现了基于 **USRP N310 硬件时间戳** 的 SX1280 FLRC 调制通信同步引擎，覆盖 FHSS 跳频序列跟踪、TDD 时分双工时序估计、硬件采样时间轴上的时钟漂移拟合、UHD Timed Commands 硬件调度及时间轴可视化。

---

## 工作台启动入口

进入“FHSS 跳频与 TDD 时序同步工作台”后，上方常驻“实机同步采集”控制栏。点击“参数设置”打开右侧抽屉，抽屉独立滚动，可用关闭按钮或 Esc 收起，主体图表不随抽屉展开而压缩。在抽屉中检查参数后，点击“启动实时同步采集”连接 SDR；选择“同步收发会话（USRP）”时，主按钮为“启动同步收发会话”。启动/停止按钮始终可见。工作台仅提供实机运行，已移除时序仿真、历史回放及其专用 API。

抽屉统一提供设备地址、采样率、主时钟、接收通道、天线、增益、同步字、码率、CR、BT 和定时跳频开关。同步收发增加发送增益、同步/回复等待时间及两种同步字极性；监听提供持续时间和 JSONL 输出路径。参数修改保留为草稿；活动任务继续使用原配置，点击“应用参数并重启”才会先停止旧任务、确认释放，再启动新任务。CLI 预览与实际启动使用同一份参数。监听 CLI 对应的物理参数为 `--bit-rate`、`--cr`、`--bt`，均传给实时解调器。

跳频配置通过“射频跳频模板”下拉选择，使用统一模板库，无需输入配置路径。选择模板会填入 OTA 同步字和表内首个监听频点；之后可手动修改。抽屉还提供“物理参数预设”，仅显示兼容 DK32S 变长头/CRC24 的物理模板，载入码率、CR、BT、同步字和帧头，采样率与频率仍沿用当前采集设置。清除物理预设保留已载入参数。可直接打开模板库管理或刷新列表；原有配置不在列表时明确提示重新选择，不自动替换。

选择 USRP 时，采样率通过下拉选择，按 125、122.88、153.6 MHz 主时钟分组，各项标明 MSps 和整数分频倍数。跨组选择会一起更新主时钟和采样率；单独切换主时钟则保留兼容速率或改用兼容候选。低于当前码率四倍的选项不可选，实际速率仍以设备回读为准。HackRF 沿用独立采样率输入。

同步会话在软件解调积压时优先追赶当前数据：队列满则回收尚未解调的待办窗口；采集中排队超过 250 ms 的窗口会跳过，停止后的残余窗口正常排空。跳窗不改写 SDR 的采样计数或 UHD 硬件时间戳，软件跳窗与硬件溢出分别统计。发生跳窗会使旧同步失效并重新捕获，收发会话在重新锁定前不能沿用旧时序发送。过载区间可能漏帧，这不是无损采集保证；增加缓冲不能解决持续的吞吐不足。

实时状态每 0.5 秒上报一次，即使没有解出帧也显示队列数量、排队时间、DSP 耗时与 10 ms 窗口步长之比，以及累计跳过窗口和时间。`sync.backlog` 日志和 `radio.backlog` 事件记录跳窗及重新捕获动作；耗时比持续大于 1 表示当前处理速度赶不上输入。独立 `live` 解调命令仍保留原有严格积压报错策略。HTML 时间轴只保留开头 100 ms 的事件用于绘制，完整帧仍按配置写入 JSONL。

诊断日志为 JSON，使用 `session_id` 关联同一次采集。`sync.started` 记录请求配置；`sync.configured` 记录实际采样率、窗口步长/重叠及队列限制；`sync.health` 每 5 秒汇总处理速度与排队高水位。跳窗日志分别给出 `queue_full_drops`（队列满）和 `stale_window_drops`（排队超时），以及最近跳过窗口的样本范围。`sync.failed`、`sync.stopped` 记录错误和结束统计，状态输出异常会记录 `sync.monitor_failed` 或 `sync.monitor_timeout`，不再静默丢失监控。双工会话的 `duplex.status` 也包含同样的积压指标，发生跳窗时额外记录 `sync.backlog`。

没有活动采集任务时显示“待机（未启动）”；启动后等待实际同步状态，再显示搜网、捕获、锁定或失锁。状态区会保留最近收到的实时状态，离开工作台再返回时继续显示当前任务的数据。

## 一、 三类时间维度的严格分离

在高速跳频与时分双工系统中，必须严格解耦以下三类物理时间维度：

1. **USRP 硬件采样时间 ($t_{\text{hw}}$)**：
   - 由 USRP N310 内部硬件时钟计数器维护，格式为 `(full_secs, frac_secs)`。
   - 完全独立于操作系统调度、Python GIL、以太网或 USB 缓冲延迟。
   - 前导物理到达时间：$t_{\text{arrival}} = t_{\text{hw\_chunk}} + \frac{k_{\text{peak}} - d_{\text{filter}}}{f_s}$。
2. **FHSS 跳频切换时间 ($t_{\text{hop}}$ 与 $T_{\text{slot}}$)**：
   - 载波驻留时间（Dwell Time）$T_{\text{slot}} = 50.0\text{ ms}$（500 个 100µs ticks）。
   - 20 个频点构成 1.000 秒的大跳频周期 $T_{\text{cycle}} = 1000\text{ ms}$。
   - 时隙索引：$\text{slot\_index} = (\lfloor T_{\text{remote}} \cdot 10000 \rfloor \pmod{10000}) // 500$。
3. **TDD 上下行交互时间 ($T_{\text{tdd}}$)**：
   - 槽内子帧重复周期约为 12.0 ms。
   - 包含地面下行发送持续期（~1.53ms，33B 载荷）、射频收发转换保护间隔（Turnaround Guard，~810µs）、空中回复期（~0.53ms）以及时隙末尾守候期（Slot Guard，~11ms）。

## 二、 协议实测与 TDD 双候选模型判定

针对两种候选模型：
- **Model A (固定周期调度，Fixed-Periodic)**：双端各自维护严格的绝对 TDMA 周期表。
- **Model B (接收触发式响应，Reception-Triggered)**：天空端仅在收到地面有效包后发起一次回复。

在真实捕获（`outputs/passive-current-20261020.jsonl` 与 `docs/data/dual-hackrf-20261020.json`）中：
1. 36 个空中回传包 **100% 紧随地面包出现**（前导到达间隔为 $2.356 \pm 0.016\text{ ms}$，转换保护时间为 $810 \pm 40\text{ }\mu\text{s}$）。
2. 未收到地面包时，空中端未发出任何独立包；遥控器关闭时，监听频点回传数为 0。
3. **实测证明当前协议运行机制为 Model B（接收触发式响应）**。同步模块同时支持两种模型的配置与解析。

## 三、 同步状态机与鲁棒性

状态机管理以下状态流转：
- `SEARCHING`：初始盲搜，搜集物理有效帧。
- `ACQUIRING`：捕获中，获取 1~2 个有效物理锚点。
- `LOCKED`：锁定跟踪，估计时钟漂移（ppm），预测时隙与载频，置信度达到 95%+。
- `HOLDOVER`：短暂丢包或深衰落保持，依靠漂移模型外推，避免漏解帧导致时钟中断。
- `LOST`：超时未收到新锚点，复位基准并重新搜索。
- **溢出与不连续处理**：当 UHD RXMetadata 报告 `OVERFLOW` 时，立即标记采样不连续，拒绝使用不可靠的采样计数外推，等待下一个有效硬件时间戳完成再同步。

## 四、USRP N310 定时跳频与提前量

N310 的射频芯片为 **AD9371**。不能将 AD9361 的锁相环建立时间当作已验证的 N310 参数。

当前实时跳频固定 RX 本振在 2450.06MHz、模拟带宽为 100MHz，使用 `rf_freq_policy=NONE` 的定时数字调谐切换 FPGA DDC。调度线程独立于解调线程，按当前硬件时钟预测未来时隙，检查命令顺序并过滤重复命令。跨调谐窗口按实际中心频率分段解调，默认丢弃调谐后的 0.5ms；该保护值是配置预算，不是已测得的模拟 PLL 建立时间。

本机 Windows/UHD 4.9 的一次硬件时间读取实测耗时约 20–32ms。调度默认要求至少 100ms 提前量，并进一步预排后续边界。缓存的硬件时间估计使用完整 RPC 往返延迟作为保守上界；时钟拟合仍使用 IQ 自身的 UHD 采样时间戳。网络提前量发生在命令执行之前，不应与执行后的射频建立时间混为同一预算。

默认只在初始监听信道解调校时，其他信道由硬件定时跟随；等待本机发送回复时解调相关窗口。库接口的 `observation_frequencies` 可增加观测信道。这个策略允许跳过大多数帧，避免将“每帧解调成功”作为跳频继续运行的条件。

TX 在启动跳频线程前初始化，后续同一本振内的频点切换仅更新数字频偏、复用 streamer。若线程延迟导致某次调谐已错过提交期限，记录 `late_tune_skips` 并重新规划未来边界，不将一次迟到变成整个接收会话的终止。

### 已验证的查询命令

接收天线连接通道 0 的 RX2，发送天线连接该通道的 TX/RX。以下命令在 N310 SFP0 上完成过真实定时跳频查询，匹配到 `0x23` 返回的 20 项跳频表（约 1.439ms 前导间 RTT）：

```powershell
python -m flrc_modem duplex --args "type=n3xx,addr=192.168.10.2" --rf-config templates/rf/current-rf-config-20261020.json --gain 40 --tx-gain 20 --antenna RX2 --timed-hopping --message-file templates/messages/dk32s_tx_get_hops.json --json
```

DK32S 天空端序号独立递增，即使 `is_ack=true` 也不回显地面序号。匹配检查方向、sum8、同步字、频点、命令、回复窗口，以及天空端序号是否相对于发送前的观测向前推进（支持 15bit 回绕）。普通周期性遥测不能据此认定为本次请求的回复。`reply_matched` 表示协议关联匹配，不声称仅凭时间邻近就证明因果关系。

`duplex --message-file` 单次模式只发送一帧，等待回复后退出。模板中的 `updates` 只用于在编码前生成字段值，不控制发送次数。例如 `dk32s_tx_rc_relay.json` 的 `sequence` 计数器 `start=100`，首次发送的实际序号为 100；同一收发机会话下一次显式发送才使用 101。调制预览和时隙重新规划不会推进这个计数器。若要使用固定序号，可删除 `updates`、保留顶层 `sequence`。

弱信号下可加 `--sync-timeout 30`，将初始同步等待及每次发送前的重新同步等待上限由默认 5 秒改为 30 秒。这个参数同时用于单次、JSONL 和交互模式；`flrc usrp duplex` 入口也支持。`--timeout` 仍只控制发送后等待回复的时间。

等待更久只增加收到有效包的机会，不降低锁定条件：目前至少需要 3 个有效地面时间锚点，覆盖至少 0.4 秒。只有射频能量或只有天空端回传不能建立地面时钟拟合。等待失败时会显示 CRC 有效帧数、地面时间锚点数、锚点跨度、溢出及接收错误。锁定后的默认 5 秒保持上限与 `--sync-timeout` 独立，不会随启动等待时间一起延长。

日志进一步区分地面帧、天空回传、解析失败、时钟观测拒绝和累计接受锚点。`CRC有效帧>0` 且当前锚点为零不代表物理层没工作：可能全部是无地面时间戳的天空回传，也可能曾经建立锚点、随后失锁清空；累计锚点和最近失锁原因可区分这两种情况。

本机远端遥控器的被动对照采集中，通道 0/RX2、2471.66MHz、40dB 接收增益下，6 秒解出 23 帧，全部为天空端 `0x16`；随后 50dB 下，8 秒解出 46 帧（地面 15、天空 31），最终锁定且无溢出。该场景可先尝试 `--gain 50 --sync-timeout 30`。增益改善取决于实际噪声、干扰和天线条件，不能由这次结果推断任意增加增益都有效。

## 4. USRP N310 主时钟 (MCR) 与采样率对齐机制

USRP N310 硬件架构中基带 IQ 采样率由其 FPGA DDC 从主时钟频率（Master Clock Rate, MCR）执行整数分频产生：
$$\text{Sample Rate} = \frac{\text{MCR}}{\text{Decimation Factor } N}, \quad N \in [1, 1024] \cap \mathbb{Z}$$

N310 官方原生支持以下三组 MCR：
1. **125.00 MHz**（UHD 默认值）：
   - 请求 2.0 MSps 时：$125 / 2 = 62.5$（非整数），UHD 硬件将强制对齐（Coerce）至 62 分频（$\approx 2.016129\text{ MSps}$，偏差 $+8065\text{ ppm}$）。
   - **推荐整除采样率**：**2.5 MSps**（50 偶数分频，通带最平坦，已设为 USRP 模式默认值）或 5.0 MSps（25 分频）。
2. **122.88 MHz**（蜂窝/LTE 标准时钟）：
   - 请求 2.0 MSps 时：$122.88 / 2 = 61.44$（非整数）。
   - **推荐整除采样率**：**1.92 MSps**（64 偶数分频，标准速率）或 3.84 MSps（32 分频）。
3. **153.60 MHz**：
   - **推荐整除采样率**：**2.40 MSps**（64 分频）或 3.20 MSps（48 分频）。

> [!TIP]
> **自适应硬件时钟对齐保护（Zero-Drift Protection）**：
> 引擎在 USRP 启动时会实时回读 UHD 的实际生效采样率（`uhd_usrp_get_rx_rate`）。即便用户显式指定了无法整除的采样率（如 2.0 MSps），解调器与硬件时间戳提取器也会自动将计算基准调整为硬件真实频率（2016129.03 Hz），彻底避免因采样率偏差累积导致的时间戳虚假漂移与解调丢包。

## 5. 交互式 TDD 同步双工收发机 (`flrc duplex`)

针对“**不模拟固定角色，在后台持续接收校准同步，用户随时按需发送自定义数据，并在精准时隙打出后接收对端回复**”的核心业务需求，系统提供了 `LiveTDDTransceiver` 与 `flrc duplex` 统一交互命令：

```powershell
# 启动交互式 TDD 双工控制台（默认连接 USRP N310 192.168.10.2）
flrc duplex --args "addr=192.168.10.2"
```

### 工作机制与流程
1. **后台持续接收与动态纠偏**：后台线程持续拉取 RX IQ 流并送入解调器，高频更新时钟漂移（ppm）与 50ms 时隙边界。
2. **状态感知按需发射**：
   - 当用户在控制台输入十六进制（如 `01 02 03 04 05 06`）或文本时，引擎评估同步状态。若处于锁定状态，根据当前时隙剩余时间自动选定当前时隙或下一时隙首部作为目标硬件时刻 $t_{\text{tx}}$。
   - 在线将载荷编码调制为 FLRC IQ 突发包，并通过 UHD TX Streamer 下发硬件时间戳指令（`has_time_spec=True`）。
3. **精准捕获对端回复**：
   - 伴随运行的 RX 流在对端回传到达时完成解调，自动计算往返时延（RTT，毫秒级），并将回复载荷实时回显至控制台。

### 单次非交互调用
```powershell
# 在同步锁定后准时发射指定数据，等待回复并以 JSON 输出
flrc duplex --args "addr=192.168.10.2" --data "010203040506" --timeout 1.0 --json
```

### 同步字极性反转（发送与回复独立配置）

极性反转按字节逐位取反（4 字节分别异或 `0xFF`）。FLRC CRC 覆盖同步字，因此收发两端必须知道实际使用的字：发送反转会自动用取反后的同步字重算 CRC；接收解码必须同时具备原字与反字两种候选。

同步收发会话固定接受**基准字和它的反字**两种候选：地面帧用基准字完成同步锁定，天空端回复即使使用反字也能被解码。发送极性和回复匹配极性是两个独立开关，互不联动，且都可在每条报文上覆盖：

| 参数 | 作用范围 | 生效时机 |
| --- | --- | --- |
| `--tx-invert-sync` | 会话默认发送极性；每条手动报文和每个编排项可用 `invert_sync` 覆盖 | 每条报文编码时 |
| `--reply-invert-sync` | 会话默认回复极性：期望天空端用反字回复；每条报文可用 `reply_invert_sync` 覆盖 | 每条报文等待回复时 |

典型场景是“地面发送用原字、天空端回复用反字”：

```powershell
# 发送保持基准字，等待反字回复；地面帧仍用基准字锁定，不会因极性反转失锁
flrc duplex --args "addr=192.168.10.2" --sync 54313253 --reply-invert-sync --session --ui-events ndjson
```

```powershell
# 反向组合：发送用反字，回复保持基准字
flrc duplex --args "addr=192.168.10.2" --sync 54313253 --tx-invert-sync --payload-hex 010203040506 --json
```

- `--sync`（或 `--rf-config` 中的同步字）是基准字；两个反转开关都相对它计算。`--reply-invert-sync` 需要明确的基准字，未配置同步字时无法确定反字。
- 会话启动后不能新增第三种同步字：解码候选就是“基准字 / 反字”这一对。发送极性与回复极性可以逐条切换，不需要重启会话；切换的是编码字和匹配字，不改变解调候选。
- 控制记录在 `request_id` / `message` / `payload_hex` / `wait_reply` 之外接受可选的布尔字段 `invert_sync` 与 `reply_invert_sync`；编排的周期任务与流程步骤同样支持，缺省沿用会话默认值。
- 结果事件 `duplex.result` 增加 `invert_sync` / `tx_sync_word_hex`（本条发送）与 `reply_invert_sync` / `reply_sync_word_hex`（本条期望的回复字）。状态事件 `duplex.status` 增加 `tx_invert_sync`、`reply_invert_sync`、`reply_sync_word`、`base_sync_word` 和 `accepted_sync_words`。
- 仅接收的 `demod` / `sync` 命令仍然只使用配置的单个同步字候选；需要接收反字时直接传入反字，或用 `duplex` 会话。发送反转与回复反转互不影响：反转发送不会改变接收候选，反转回复也不会改变发送字。

## WebUI 常驻收发会话

在命令控制库选择“报文收发 → 同步时隙收发（USRP）”，明确 USRP 定位参数、通道和接收参数，启用 `session` 并启动。建立会话只持续接收和同步，不会发送参数表中的初始模板。在任务中心选择 JSON 模板或原始 Hex，点击“投递一条报文”；同一设备和同步引擎可连续处理多次交互。

命令参数中的“发送同步字极性反转 / 回复同步字极性反转”决定会话默认值。会话面板在投递或加入编排时可分别勾选“反转发送同步字极性”和“反转接收回复同步字极性”，只影响这一条报文；编排中的每个周期任务和流程步骤也各自保留这两个选项，展开卡片可修改。设备与同步详情显示当前解调接受的同步字、按会话默认计算的回复同步字与回复极性。交互记录会为每条结果标出实际发送极性、期望回复字及是否反转。

每个请求有唯一编号和独立结果：`tx_completed`（不等待回复）、`reply_matched`、`reply_timeout`、`send_failed`、`rejected`、`cancelled` 或 `interrupted`。`tx_completed=true` 与 `reply_matched=true` 分别表示发送完成和回复匹配；回复超时不视为交互成功。失锁会触发本次发送前重新等待，不能使用旧快照强行发送。停止会话时取消尚未提交的发送，先释放设备再结束任务；未收到最终确认的请求标为中断，不自动重发。

启用 `--timed-hopping` 后，超过保持时限未收到地面物理时间锚点时，会话会自动排入返回初始观测频点的调谐命令，并等待重新捕获。返回命令排在已提交的 RX 跳频命令之后；返回及调谐稳定前缓存的旧帧不能用于恢复锁定。获得新的有效锚点并重新锁定后，后台自动恢复跳频，恢复期间禁止使用旧时序规划发送，无需重启会话。持续弱信号或设备不再发出锚点时仍会停留在搜索状态。

状态事件中的 `receive_frequency_hz` 表示按已提交调谐时间表推算的当前 RX 频点，`reacquiring` 表示正在返回或重新捕获，`reacquisition_count` 为本次会话的重捕获次数。原有 `frequency_hz` 是同步模型的预测频点，未锁定时为占位值。WebUI 会话面板显示 RX 频点和重捕获次数。`--sync-timeout` 控制一次发送等待锁定的时长，不改变同步状态机的 5 秒锚点保持时限。

CLI 的 `duplex --session --ui-events ndjson` 使用 stdin 控制协议，输出 NDJSON 事件。普通请求例如 `{"request_id":"query-1","message":{"direction":"ground_to_air","command":"0x23","fields":{"data_hex":""}},"wait_reply":true}`；原始载荷使用 `payload_hex` 替代 `message`。`{"action":"stop"}` 取消队列并结束会话，普通 stdin EOF 则排空已接收请求后退出。单次和原有 `--stdin-jsonl`/REPL 入口继续保留。

### 周期发送与交互流程混合编排

任务执行中心默认使用精简任务列表，可展开列表详情；宽屏支持隐藏列表。“专注输出”暂时隐藏执行历史和同步会话，恢复工作区后保留原来的编辑内容。执行历史、任务详情、事件载荷和文件路径按需展开；终端日志支持本地搜索、输出流过滤和自动换行。事件列表优先显示最新的 50 条，可搜索或继续加载。

任务输出窗口可拖动标题上下移动，仅在靠近任务中心底边时自动吸附；其他位置保持松手时的位置。拖动上沿可调节高度，悬浮时也可拖动下沿。双击分隔条恢复默认布局；位置、高度和收起状态保存在本机。键盘聚焦移动区后使用上下方向键微调，Home 移至顶部、End 吸附底部；聚焦高度分隔条后使用方向键调整高度，Home 收起、End 拉高。

常驻会话分为“报文编辑 / 发送编排 / 交互记录”三个工作区，设备信息默认折叠。会话整体可收起，也可放大编辑区域；切换工作区、收起会话或专注输出不会卸载已挂载的编辑器。先在“报文编辑”选择模板或输入 Hex，点击“加入周期任务”或“加入流程步骤”；每次加入都会保存当前报文和等待回复选项的副本，之后编辑原报文不会修改已加入的任务。

“发送编排”中的任务以折叠卡片展示，展开即可编辑各自的 JSON / Hex 报文，支持格式化、保存或取消修改。未保存的报文修改会阻止启动，避免发送旧内容。周期任务可配置目标周期和执行次数（0 表示持续）；流程步骤可配置步骤前等待、等待回复、失败后停止整个编排或继续下一步，并设置整个流程的循环次数。任务可复制、移除，步骤可上下移动；“载入上次编排”可恢复最近一次执行的配置，重新启动时使用新的编排编号。运行期间展示本次执行配置并锁定编辑。

点击一次“开始编排”后，执行器驻留在收发子进程中，浏览器切换页面或关闭后继续执行。周期任务与流程步骤按最早到期时间交错执行，步骤等待期间不阻塞周期任务；同时允许手工投递单条报文。每次只执行一个收发交互，等待匹配回复会占用这个执行通道。失败步骤默认停止整个编排（包括周期任务）；周期任务失败会记录结果，后续周期仍可执行。不会自动重试失败的查询或配置；手动重跑使用新的编排编号。

**目标周期是主机单调时钟上的调度间隔，不是精确的空口发包间隔。** 当前收发路径仍在约 150ms 后寻找可用硬件 TDD 窗口，提交至少保留 100ms 提前量，并等待发送完成。它适合自动执行流程及较慢的周期业务，不能据此保证 10–50ms 连续发包。周期基准不随单次交互耗时漂移；同步等待、回复等待或调度拥塞造成错过的周期会跳过，恢复后不会集中补发。有限的 `count` 统计实际执行尝试数，不统计跳过的周期；最多 8 个周期任务、64 个流程步骤，每个编排最多执行 10000 次。

“停止编排”只停止此编排，保留会话的接收、同步与手动发送。尚未提交硬件的发送会取消；已经提交的定时发送可能仍会发出，不能把停止按钮视为撤回硬件命令。停止等待回复时保留已经确认的 `tx_completed`，不会误报回复成功。结束会话或子进程异常退出后，未确认的编排标为 `interrupted`，不会在重跑会话时自动恢复。

每次执行结果包含 `plan_id`、`source`（`periodic` / `step`）、`item_id`、流程轮次，以及计划调度时间偏移、实际执行开始偏移、调度迟到和跳过周期数。上述偏移以主机编排启动时间为零点；`tx_hw_time` 则是实际规划的 USRP 硬件时间，两者不能直接相减。最近 50 条交互结果、编排统计与配置可在会话面板查看，所有执行事件保留在当前任务执行轮次的结构化事件记录中。

REST 控制入口为 `POST /api/v1/runs/{run_id}/plan`，与 CLI stdin 使用相同控制记录：

```json
{
  "action": "start_plan",
  "plan": {
    "plan_id": "mixed-demo-1",
    "periodic": [
      {
        "id": "channels",
        "interval_ms": 500,
        "count": 20,
        "message": {
          "direction": "ground_to_air",
          "command": "0x11",
          "fields": {"channels_raw": [1024,1024,1024,1024,1024,1024,1024,1024,1024,1024,1024,1024,1024,1024,1024,1024]}
        },
        "wait_reply": false
      }
    ],
    "steps": [
      {
        "id": "query-hops",
        "delay_ms": 1000,
        "message": {"direction": "ground_to_air", "command": "0x23", "need_ack": true, "fields": {"data_hex": ""}},
        "wait_reply": true,
        "on_failure": "stop"
      }
    ],
    "cycles": 2
  }
}
```

停止记录为 `{"action":"stop_plan","plan_id":"mixed-demo-1"}`。同一会话只允许运行一个编排，相同 `plan_id` 不能重复执行；整个控制记录不能超过 64KiB。编排执行的 `request_id` 使用保留前缀 `@plan:`，手动请求不能使用此前缀，避免结果编号冲突。`GET /api/v1/runs/{run_id}/session` 返回最近的 `plan` 状态、`plan_definition` 配置与 `plan_rejection` 控制拒绝记录。CLI 输出 `duplex.plan.definition`、`duplex.plan`、`duplex.plan.rejected` 和附带编排来源的 `duplex.request` / `duplex.result` 事件。stdin EOF 会继续排空已接受的编排；持续周期任务会运行到停止或达到 10000 次上限，批处理应显式设置有限 `count`。

WebUI 的 `POST /api/v1/runs/{id}/messages` 返回 accepted 仅代表请求进入控制管道，最终执行结果由 `duplex.result` 事件和会话面板给出。每个会话最多接收 10000 个不同请求编号，最多 16 个未完成请求；重复编号被拒绝。历史结果与状态分开查询，长时间的同步状态更新不会挤掉最近的交互结果。

物理配置可读取共用 TOML，但目前时钟锚点、跳频周期、TDD 规划和回复匹配均基于 DK32S。固定头、CRC32 等其他模式会在启动前明确拒绝，需先实现对应协议的同步模型；物理层盲发和离线调制可以使用这些成包参数。
